  <action>
Create `server/api/traits.go`:

1. A `TraitsHandler` struct holding `*db.Queries`:
   ```go
   type TraitsHandler struct {
       queries *db.Queries
   }
   func NewTraitsHandler(queries *db.Queries) *TraitsHandler
   ```

2. `RegisterRoutes(mux *http.ServeMux)` method:
   - Register `GET /api/v1/clients/{hostname}/traits` -- Go 1.22+ pattern matching
   - This is more specific than the catch-all `/api/` in gateway.go, so it takes priority in ServeMux

3. `HandleGetTraits(w http.ResponseWriter, r *http.Request)`:
   - Extract hostname from `r.PathValue("hostname")`
   - Call `queries.GetClientByHostname(ctx, hostname)`
   - If error (pgx.ErrNoRows): return 404 JSON `{"error": "client '<hostname>' not found"}`
   - Call `queries.GetLatestClientFacts(ctx, client.ID)`
   - If error (pgx.ErrNoRows): return 404 JSON `{"error": "no traits available for '<hostname>' -- client has not reported traits yet"}`
   - Return 200 JSON:
     ```json
     {
       "hostname": "web01",
       "collected_at": "2026-03-07T10:30:00Z",
       "traits": { ... raw traits object ... }
     }
     ```
   - Use `json.RawMessage` for traits to avoid double-encoding (the DB already stores JSON)
   - `collected_at` formatted as RFC3339 from `ClientFact.CollectedAt`
   - Set `Content-Type: application/json`

4. Wire into `gateway.go`:
   - In `NewGateway`, before the bootstrap handler registration, add:
     ```go
     traitsHandler := NewTraitsHandler(queries)
     traitsHandler.RegisterRoutes(mux)
     ```

Create `server/api/traits_test.go`:
   - Use `httptest` with a mock or in-memory approach
   - Test the three scenarios: success, client not found, no facts
   - Since queries use pgx and sqlc, create a test helper that implements the needed interface or use a test-double approach. The simplest: test the handler with a real test DB via `pgxpool` if the project has that pattern, or mock the Queries struct. Given sqlc generates concrete methods on `*Queries`, the practical approach is to test the handler response parsing logic and the integration via `go test` against the handler directly with a mock DB connection. If mocking is complex, test at the HTTP level with a helper that stubs the Queries methods. Check existing test patterns in the project.

Note: If mocking Queries is impractical (sqlc generates concrete struct methods, not interfaces), focus tests on: (a) the response JSON structure, (b) the dot-path traversal in gvctl, and (c) build verification. The handler integration will be verified by the end-to-end `gvctl` test in the verification step.

  <action>
Add to `cli/clients.go`:

1. A `clientsTraitsCmd` cobra.Command:
   - Use: `traits <hostname> [dot.path]`
   - Short: `View collected traits for a client`
   - Args: cobra.RangeArgs(1, 2) -- hostname required, dot-path optional

2. RunE logic:
   - hostname = args[0]
   - Call `client.get("/api/v1/clients/" + hostname + "/traits", &resp)` where resp is:
     ```go
     var resp struct {
         Hostname    string         `json:"hostname"`
         CollectedAt string         `json:"collected_at"`
         Traits      map[string]any `json:"traits"`
     }
     ```
   - If error from get (which already formats the server error message): return the error directly -- the server's 404 message is already clear
   - If len(args) == 2 (dot-path provided):
     a. Call `traverseDotPath(resp.Traits, args[1])`
     b. If not found: return `fmt.Errorf("trait path '%s' not found", args[1])`
     c. Call `formatTraitValue(value)` and print to stdout
   - If len(args) == 1 (no dot-path):
     a. Pretty-print the entire response (the envelope) as JSON with 2-space indent
     b. `json.MarshalIndent(resp, "", "  ")`

3. Helper functions (unexported, in cli/clients.go):
   - `traverseDotPath(data map[string]any, path string) (any, bool)` -- same logic as agent version: split on `.`, walk map
   - `formatTraitValue(v any) string` -- string/number/bool returns `fmt.Sprint(v)`, map/slice returns pretty JSON

4. In `init()`: add `clientsTraitsCmd` to `clientsCmd.AddCommand(...)` call

Note: The dot-path traversal is duplicated from the agent's implementation by design -- these are separate binaries with no shared internal package, and the function is ~15 lines. This avoids introducing a new shared package for trivial code.
