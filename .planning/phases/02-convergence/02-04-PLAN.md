  <name>Task 1: DAG construction and topological sort with Kahn's algorithm</name>
  <files>agent/runner/dag.go, agent/runner/dag_test.go</files>
  <behavior>
    - TopoSort with no dependencies returns resources in input order
    - TopoSort with linear chain (A->B->C) returns [A, B, C]
    - TopoSort with diamond (A->B, A->C, B->D, C->D) returns valid topological order
    - TopoSort with circular dependency (A->B->C->A) returns error naming the cycle participants
    - TopoSort with unknown dependency (A depends_on X which doesn't exist) returns error
    - BuildDAG normalizes subscribes to notify: if resource B subscribes to A, A's notify list gets B added
    - BuildDAG flattens module-level and resource-level depends_on into a unified graph
    - Resource struct for DAG: Name, Type, Params, DependsOn, Notify, Subscribes, When, ModuleName
  </behavior>
  <action>
    Create `agent/runner/dag.go`:

    Define `ResourceNode` struct used internally by the runner:
    ```go
    type ResourceNode struct {
        Name        string
        Type        string
        Params      map[string]string
        DependsOn   []string
        Notify      []string
        Subscribes  []string
        When        string
        ModuleName  string
    }
    ```

    Implement `BuildDAG(modules []*pb.Module) ([]ResourceNode, map[string][]string, error)`:
    - Flattens all modules into a list of ResourceNodes
    - For resource-level metadata: reads `_depends_on`, `_notify`, `_subscribes`, `_when` from params (set by server in Plan 03), or reads directly from Module fields for module-level metadata
    - Normalizes subscribes -> notify: for each resource with subscribes, find the subscribed resource and add current resource to its notify list
    - Returns: sorted resources list, notify map (resource name -> list of names to notify), error
    - The notify map is separate from the sorted list so the runner can process notifications after execution

    Implement `TopoSort(nodes []ResourceNode) ([]ResourceNode, error)`:
    - Build adjacency list from DependsOn
    - Compute in-degrees for all nodes
    - BFS from zero-in-degree nodes (Kahn's algorithm)
    - If result length != input length: cycle detected -- identify cycle participants by finding nodes still with in-degree > 0, return error: "circular dependency detected among resources: [names]"
    - Validate all dependencies exist: if DependsOn references a name not in the node set, return error: "resource %q depends on unknown resource %q"

    Tests:
    - No deps: preserves input order
    - Linear chain: correct order
    - Diamond: valid topological ordering
    - Circular: error with participating resource names
    - Unknown dep: error with helpful message
    - Subscribe normalization: B subscribes A -> A's notify list includes B
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Runner that executes resources in DAG order with notify/subscribe triggers</name>
  <files>agent/runner/runner.go, agent/runner/runner_test.go</files>
  <behavior>
    - Runner executes resources in topological order
    - Runner evaluates when: condition before each resource, skips with ActionSkipped if false
    - Runner records ResourceResult for each resource (including skipped)
    - Runner collects changed resources after main pass, then re-executes notify targets
    - Notify targets are force-executed even if they would be a no-op (e.g., service restart)
    - Runner supports dry-run mode (passed through to executors)
    - Runner supports single-module filter (only execute resources from named module)
    - Runner returns []ResourceResult for all executed resources (main pass + notify pass)
    - Runner continues on individual resource error (does not abort entire run)
    - Resources that errored do NOT trigger their notify targets
  </behavior>
  <action>
    Create `agent/runner/runner.go`:

    Define `Runner` struct:
    ```go
    type Runner struct {
        Executors map[string]modules.Executor  // keyed by resource type: "file", "package", etc.
        Facts     map[string]any
        DryRun    bool
        Module    string   // if non-empty, only execute resources from this module
    }
    ```

    Implement `Run(ctx context.Context, protoModules []*pb.Module) ([]modules.ResourceResult, error)`:
    1. Call `BuildDAG(protoModules)` to get sorted resources and notify map
    2. Call `TopoSort(resources)` to get execution order
    3. If `Module` is set, filter sorted list to only resources from that module
    4. **Main execution pass:**
       - For each resource in sorted order:
         a. Evaluate `when` condition via `EvaluateWhen(resource.When, r.Facts)` -- if false, record ActionSkipped and continue
         b. Look up executor by `resource.Type` in `r.Executors` map -- if not found, record error and continue
         c. Call `executor.Execute(ctx, resource.Params, r.DryRun)` -- set ModuleName, ResourceType, ResourceName on result
         d. Collect result
    5. **Notify pass** (only if not dry-run):
       - Collect names of all resources that had `Changed=true` and no error
       - For each changed resource, look up its notify targets in the notify map
       - Deduplicate notify targets (a resource may be notified by multiple changers)
       - For each unique notify target, re-execute it with the executor (force apply)
       - Append notify results to the results list
    6. Return all results

    Implement `NewRunner(executors map[string]modules.Executor, facts map[string]any, dryRun bool, module string) *Runner`

    Tests use mock executors that record calls and return canned results:
    - Sequential execution in topological order (verify call order)
    - when=false skips resource with ActionSkipped
    - Changed resource triggers notify target re-execution
    - Error resource does NOT trigger notify
    - Dry-run mode: executors called with dryRun=true, no notify pass
    - Single-module filter: only matching resources execute
    - Unknown resource type: error recorded, execution continues
    - Subscribes normalization works end-to-end via BuildDAG -> notify map
  </action>
