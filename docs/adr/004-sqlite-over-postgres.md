# ADR-004: SQLite over Postgres

**Status:** Accepted  
**Date:** 2025-01-01 (retroactive)

## Context

The server needs persistent storage for enrollment records, convergence history, run results, sessions, and other operational data. The choice between embedded and external databases has significant deployment implications.

## Decision

Use SQLite with WAL mode as the sole database. Schema managed by golang-migrate, queries generated by sqlc.

## Consequences

- Zero external dependencies — no database server to install, configure, or maintain
- Single-file backup: copy the `.db` file
- WAL mode enables concurrent reads with a single writer, sufficient for the expected write patterns (check-in results, trait updates)
- sqlc provides type-safe Go from SQL — compile-time query validation
- Trade-off: single-writer means write throughput is bounded. For Vigo's workload (thousands of envoys checking in), this is fine — writes are small and fast
- Trade-off: no built-in replication. HA would require an external solution (Litestream, rqlite, etc.)
- Deployment simplicity outweighs scaling concerns at current and near-term scale

## Alternatives considered

- **PostgreSQL** — rejected because it adds an external dependency, complicates deployment (Docker + Postgres), and Vigo's workload doesn't need its concurrency model
- **etcd/Consul** — rejected because Vigo isn't a service discovery tool; a relational model fits the data better
