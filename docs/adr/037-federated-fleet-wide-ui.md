# ADR-037: Federated fleet-wide UI for spanner (any-bolt-federates read model)

**Status:** **Withdrawn / Reverted (2026-06-27, 0.76.59).** The entire federated-UI arc (interim labeling `00a040f5` through the "D" redesign at 0.76.58 — scope tabs, the `/fleet/*` aggregate section, per-bolt route-to-owner, and the five `Get{Security,Risk,Compliance,Health}Summary` / `GetScopedPageData` VigoAdmin read-RPCs) was rolled back to the pre-arc baseline (`8fdb28c3`). **Reason:** on a real 2-bolt spanner the federated experience didn't carry its weight — the per-bolt page chrome plus a parallel `/fleet` section was more surface than the payoff. The product decision is the opposite of this ADR: **each bolt's web UI shows only its own local partition**, and an operator who wants another bolt's view opens that bolt's UI directly. The spanner *control plane* (roster gossip, peer membership, auto-admission, the convergence/envoy/runs fan-out that predates this arc) is unaffected. This document is retained for the decision record; the design below is no longer implemented.

**Original status (for the record):** Approved — implementation in progress (grilled 2026-06-25; the grill corrected the per-slice merge math below and inverted the build order to **tabs-first**). Shipped: interim labeling (`00a040f5`), tab shell (slice 1), federated Security Posture (slice 2), federated Risk (slice 3), the federated **Standards Compliance dashboard card** (slice 4a, 0.76.40), and slices 5/5b + the "D" relocation through 0.76.58 — all now reverted.

### Slice 5 — generic route-to-owner page data (0.76.42)

Per-bolt page tabs do **not** need a typed federated RPC per page. A peer bolt already has a full handler that builds its own page from its own `fleetIndex`/`configStore`/audit-chain, so to render "bolt-2's /security page" the viewer asks bolt-2 to build it and renders the result in the viewer's own chrome. One generic leaf RPC `GetScopedPageData(page_id) → json` serves every page: the owner builds its `ui.<Page>Data` via the same `DataSource` the local UI uses and JSON-marshals it; the viewer unmarshals into the same type and renders. This **dodges slice 4b for the per-bolt case** (the owner builds its own compliance report; its audit-chain renders per-bolt naturally) and ships nothing continuously — pull-on-view only, ADR-compliant. Mechanics: `DataSource.<Page>Data` is the SoT (local render + RPC share it); `routeScopedPage` (ui) decides local-vs-route by scope; `ScopedPageDataFromBolt` (spanner) is the single-peer fetch (the `RunsFromBolt` shape). Fleet-scope of the aggregate pages reuses the existing card summaries (no deep merge); list pages (envoys/runs) use the existing `Aggregate*Fanout` + an owning-bolt column. Drill-downs (cert detail, live security-drawer query, CVE search) route to the owning bolt by envoy-ID — the slice-5 long tail.

**Fleet-aggregate render pattern (0.76.43).** A page's Fleet view is the **one canonical summary extended** — never a second aggregation path. For Security: `SecuritySummary` (the object the dashboard card already merges) gained the page's summable scanner rollups, with **sum+count for the Lynis average** so the viewer re-means correctly (not an average-of-averages). The Fleet render (`securityFleetPageData`) maps the merged summary into the page struct with per-entity slices empty + a `FleetAggregate` flag; the template hides per-host tables, cert drill-downs, CVE search, and trends (none aggregate at scale) and shows a "select a bolt for per-host detail" note. Scalar rollups + the deduped fleet CVE list render real merged numbers. Every remaining aggregate page (Risk, Agent-Health) follows this exact pattern: extend its canonical summary (sum+count for any average, top-N candidates where it has a ranking), render the Fleet view from it, omit per-entity detail with a drill-to-bolt note. Compliance needs the least — its landing summary already federates (slice 4a); the framework reports stay per-bolt/deferred (4b).
**Date:** 2026-06-24 (merge-math + sequencing corrections 2026-06-25).

## Context

In spanner mode every rich UI page — dashboard cards, envoys, CVE, risk, compliance, cert-expiry, agent-health — reads the local `DataSource` (this bolt's own FleetIndex/DB), so it shows only **this bolt's partition**. The only federation-wide view is `/spanner`, and it can aggregate solely because count + convergence are the only things peers gossip (`FleetSnapshot{Envoys []EnvoyLite, Convergence ConvergenceCounters}` — no traits/CVE/risk/compliance). The visible symptom: a 2-bolt fleet where the dashboard reads 1038 and `/spanner` reads 2056, with nothing telling the operator which is which.

This breaks the product's headline deliverables. "What is our PCI coverage / CVE exposure / risk posture / cert-expiry exposure?" are inherently **org-level** questions; with per-bolt-only views the operator must open N tabs and hand-merge — and not by simple addition (compliance % is a weighted average, CVE exposure needs dedup, risk is a distribution). The compliance report / cyber-insurance PDF are sold as organization-wide; generated per-bolt they are partial reports an auditor cannot use. Federating to handle *more* envoys would therefore degrade the product at its primary job — self-defeating. The hostname-pattern partition is an arbitrary sharding detail the operator never chose; a security question has no reason to be scoped to it.

## Decision

A centralized fleet-wide UI, built on a **peer-equal "any-bolt-federates" read model** — no hub, no aggregator node. Whichever bolt the operator reaches renders the fleet view by fanning out to its peers on demand over the existing `PeerDialer` + cpauth/mTLS channel (the admission roster pins each peer's pubkey). This preserves ADR-026 peer-equality: there is no special node, one login / one session / one cert / one tunnel reaches the whole fleet.

### Data model — on-demand fan-out of per-page summaries

When a fleet-scoped page loads, the viewing bolt fans out to each peer asking for **that page's summary**, computed locally by each bolt from its own data, and merges the returned summaries. What crosses the wire is kilobytes of rollup per bolt per page view, **only when a human is on the page**. The raw ~150 KB/envoy inventory is **never** replicated to peers — that would erase the partition's memory scale-out (the whole reason to federate).

This is **not** a generic query envelope. The cross-bolt channel is hard-typed gRPC `VigoAdmin` over `PeerDialer` (`server/spanner/peerconn.go`), so each fleet page needs **one typed RPC** (request/response in `protobuf/vigo.proto`, a handler on `AdminService` that dispatches to a local summary computation, and an `Aggregate<Thing>Fanout` wrapper over the generic `fanOut` driver, `server/spanner/adminreads.go`). Auth is free: the interceptor blanket-gates the whole `/vigo.VigoAdmin/` prefix through `cpauth.Verify` + roster-pin (`server/grpc/interceptor.go`), so a new read RPC rides the same mechanism as the existing mutating RPCs with no new auth code.

### Per-page class rules

- **Aggregate/reporting pages** (dashboard top-line, CVE, risk, compliance, cert-expiry, convergence): fan-out summaries + merge.
- **List pages** (envoys): fan-out + concatenate, with an **owning-bolt column**. Cheap columns can ride the already-gossiped `EnvoyLite`.
- **Detail pages** (one envoy / one run): **route to the owning bolt**, no merge — the roster resolves the owner (`OwningBoltHostname`).
- **Write actions** (push / revoke / delete / reassign): route to the owning bolt, reusing the existing spanner admin routing (`ForcePushToBolt`, `ReassignEnvoy`, `DeleteEnvoyToBolt`, `RevokeEnvoyToBolt`). All four exist and are tested — including delete/revoke owning-bolt routing + the FleetIndex-miss `NotFound` backstop, closed in `4f23a18b` (the ADR's original "`DeleteEnvoy` has no routing" note is now stale).
- **Stateful/interactive pages** (scrier sessions, AI chat streaming): route to the owning bolt — they are inherently single-target and never merge.

### UX — Fleet + per-bolt tabs, federated-rendered

Top tabs `Fleet | bolt-1 | … | bolt-N`, all rendered **in the viewing bolt's own chrome** via federated reads (a `bolt-N` tab is the viewing bolt fetching bolt-N's data scoped to one bolt — the same RPCs, fanned to one peer instead of all). It is **not** a reverse-proxy of each bolt's literal served UI: proxying a full authenticated app (sessions, locked CSP `'self'`, scrier websockets, AI streaming) is heavy and fragile, and iframe/link-out is blocked by CSP, the per-bolt self-signed certs, and needing a tunnel per bolt. The tabs framing is strictly better than a binary "this-bolt ⇄ fleet" toggle — you can focus *any* bolt, not just the one you landed on. Default scope in spanner mode is **Fleet**.

Graceful partial results: the `fanOut` driver already gives this — a 5s per-peer timeout + panic isolation, returning partial results. Reachable bolts render; unreachable bolts are flagged ("N bolts unreachable") so a merged number is never *silently* undercounted.

**Stable chrome from one bolt up (0.76.41).** The `Fleet | <bolt>` strip renders in **standalone mode too**, not just spanner — a standalone server shows `Fleet | <hostname> (this bolt)` synthesized from `server.hostname` (falling back to `localhost`). This keeps the dashboard layout identical whether you run one server or many, so enabling spanner and adding a second bolt grows the strip by a tab rather than restructuring the page. The standalone tabs are **cosmetic**: both render the full local dashboard (the scope is never "scoped away"). Crucially, the same is true for a **single-bolt spanner** — with no peers to federate from, its Fleet view IS the full local dashboard, not the reduced federated render; routing a lone bolt to the reduced view would needlessly hide ~80% of the cards. The reduced federated Fleet view engages only once a second bolt joins (`scopedAway` gates on `len(roster) > 1`). Note the tab strip is rendered only on the dashboard today (`dashboard.html`); other pages populate `ScopeTabs` but don't yet emit it.

## What is already solid (verified) vs. what must be built

**Solid — reuse as-is:**
- Transport: long-lived mTLS gRPC `VigoAdmin` via `PeerDialer`. **Prerequisite (not a code gap, but unflagged in the original draft):** `PeerDialer` mTLS requires every bolt to share one **fleet CA** (`buildClientTLS` trusts a single `RootCAs` anchor — no skip-verify); cross-bolt fan-out fails `x509: unknown authority` without it. Establishing the shared CA is currently a **manual** operator step (`vigocli spanner ca export|import`, or `setup-bolt.sh` seeding); the hands-off `spanner.peers` boot-time auto-admission is **not yet shipped** (the field is defined but unconsumed — tracked in `pending.md`). ADR-037 is not gated on auto-admission — it works on any spanner whose bolts already share a CA (proven live on the GCP 2-bolt spanner, 2026-06-24) — but a fresh multi-bolt fleet needs the CA established first.
- The `fanOut` scatter driver + per-field merge + local fold-in is the canonical pattern (proven by `ListEnvoys` / `GetConvergenceSummary` / `ListRuns`). Do not invent a new aggregator.
- Auth: any new `VigoAdmin` read RPC is auto-gated by cpauth + mTLS + roster-pin.
- Convergence is already federated end-to-end.
- The scoring kernels (`server/cve`, `server/risk`, `server/certexpiry`, `server/convergence`) are pure and reusable; precedent for trusting cross-bolt aggregation already exists (license `aggregate` mode).

**Must be built — sized by difficulty. Build order is tabs-first (see below), not this numbering:**
1. **Convergence** — done (already fanned-out + merged).
2. **Cert-expiry + running-CVE summaries** — *small.* The fns already exist as standalone `*DataSource` methods (`RunningCVESummary`, `CertExpirySummary` in `server/fleet/datasource.go`) — no extraction from a tangled method needed, just a proto shape and an `Aggregate*Fanout` wrapper that calls the existing method locally. Both are additive (cert buckets/`PerHost` are disjoint per envoy; `RunningCVESummary` is host-scoped running-process counts). **Caveat — two different CVE metrics:** the dashboard's headline *CVE exposure* is **unique CVE IDs**, served by a *third* method `CVEData` that deduplicates by CVE-ID across hosts (max-severity reconciliation) — that one is **not** summable, so its fan-out must ship each bolt's `{CVE-ID → max-severity}` set and dedup at the viewer. Only `RunningCVESummary` is the trivial-summation case.
3. **Risk summary** — *medium.* `risk.ScoreFleet`/`ScoreEnvoy` are pure, but the per-bolt summary is embedded in `DataSource.RiskData`. The merge is non-trivial: `AvgScore` is a mean (not summable) — each bolt ships **count + score-sum**, the viewer re-means; top-N ships per-bolt candidates and the viewer re-ranks; the sparkline is per-bolt DB history (`ListRiskPostureHistory`) that must also be merged.
4. **Compliance coverage** — split into two tiers when built (2026-06-25):
   - **4a. Dashboard Standards Compliance card — DONE.** Did **not** need the `report.go` extraction the original draft feared. The dashboard headline numbers come from `computeStandardsSummary` → the `compliance_history` **snapshot** (a SQL read + the pure `aggregateComplianceSnapshot` fold), not from `BuildFrameworkReport`. So this federates exactly like risk: a `GetComplianceSummary` leaf RPC ships each bolt's per-bucket counts + `PctSum`/`PctCount` (the un-divided unweighted-mean numerator/denominator), and the viewer re-means over the union (`AggregateComplianceFanout` + `MergeComplianceSummaries`, `ComplianceFederated` template flag). The single SoT is `fleet.DataSource.ComplianceSummary` — the local dashboard delegates to it too, so local and Fleet can't drift. **Merge semantics (Option A, partition-summed):** a framework on N bolts contributes N instances; the honest headline is the re-meaned **percent**, the bucket counts are partition-summed remediation volume.
   - **4b. Auditor-grade per-control fleet report — REMAINING.** The org-wide compliance **report / cyber-insurance PDF** is where per-control dedup actually matters, and it is the larger slice that *does* touch `BuildFrameworkReport`/`aggregateFleetPartitions`/`buildFrameworkCoverage` in the ~4400-line `server/api/report.go`. **Merge math:** ship each bolt's `{framework → {control → status}}` (bounded — controls, not envoys) and reconcile **per control** across bolts (worst-wins / weighted — settle the rule per Open Questions); only the per-control `{FleetCovered, FleetTotal}` counts are truly additive (merged % = ΣFleetCovered / ΣFleetTotal). **Wire discipline (load-bearing):** fold to per-control counts *before* the wire — shipping per-envoy configcrate-assignment sets re-replicates inventory-scale data and defeats federation. **Per-bolt audit-chain status does not aggregate** — see Open Questions.
5. **Fleet + per-bolt tabs UX.** (The `DeleteEnvoy` owning-bolt routing the original draft folded in here was already shipped in `4f23a18b` — see Per-page class rules.)

**Build order — tabs-first.** The cheapest end-to-end slice that proves the whole mechanism (the `?scope=` threading, the boosted-nav tabs, fan-out-to-one-peer) is the tab shell wired to the data that is *already* federated — convergence + envoy counts/list. Build that first so the operator gets working `Fleet | bolt-N` tabs early; not-yet-federated cards carry an honest per-card scope label until their slice (2 → 3 → 4) lands and lights them up. This inverts the original tabs-last numbering.

Optionally, a `local`/no-RPC path for these pages (like convergence's gossip-cache aggregate) would require extending the gossiped `FleetSnapshot` beyond `Envoys`+`Convergence`. Not needed for v1 — fan-out-only is correct for on-demand viewing and avoids the continuous bandwidth/memory cost.

## Rejected alternatives

- **Designated aggregator / console node** — reintroduces a hub: single point of failure, one box holding everything, violates the peer-equal axiom.
- **Gossip everything (CVE/risk/compliance pushed continuously)** — continuous bandwidth + memory even when nobody's looking, always stale, and tempts replicating traits → defeats the partition's scale-out.
- **Reverse-proxy each bolt's literal UI behind a tab** — heaviest, most fragile surface (cross-bolt sessions/CSP/websockets/streaming).
- **iframe / link-out per bolt** — blocked by CSP `'self'`, per-bolt self-signed certs, and per-bolt tunnels.
- **Binary "this-bolt ⇄ fleet" toggle** — strictly worse than per-bolt tabs (can't focus an arbitrary bolt).

## Open questions / residual

- **Fleet-wide compliance is the hard slice.** Each bolt has its own tamper-evident audit hash chain; there is no single fleet audit chain, so a merged compliance view cannot present one aggregate "audit status." Resolution (deferred to the compliance slice): present coverage % merged across bolts but surface audit-chain status **per bolt** (not aggregated), with the merged report stating that the audit chain is per-bolt by construction. This is a fact about the design, not a defect — but it shapes how the compliance slice renders.
- **Per-control `Status` divergence across bolts (compliance slice).** A control's `Status` (satisfied / waived / partial / not-satisfied) is partly a *bolt-local* product-findings verdict (`buildFrameworkFindings`), so two bolts can legitimately report different statuses for the same control. The correct cross-bolt reconciliation rule (worst-wins? coverage-weighted? per-bolt breakdown on hover?) is unspecified and must be settled when slice 4 is built. The additive `{FleetCovered, FleetTotal}` counts are unaffected — this is only about the qualitative per-control verdict.
- **Shared-CA prerequisite (transport).** Fan-out presupposes the bolts share a fleet CA; hands-off establishment (`spanner.peers` boot-time auto-admission) is tracked separately in `pending.md` and is not part of this arc. Manual CA setup is the interim path.

## Consequences

Multi-slice arc; each page is one typed RPC + a small-to-large extraction. No new architecture — the federated-read machinery, auth, and merge pattern already exist and are proven for convergence/envoys/runs. The interim labeling (`00a040f5`) keeps the per-bolt views honest until the Fleet tab lands.
