# Architecture Decision Records

Short documents capturing significant design decisions and their rationale. Each ADR explains what was decided, why, and what alternatives were considered.

ADRs are immutable in their decision content. If a decision is reversed, write a new ADR that supersedes the old one rather than editing it. Terminology refreshes may be applied in-place with an `**Updated YYYY-MM-DD:**` note in the header that explains what changed — the decision and rationale stay frozen.

- [ADR-019: Gitback founder-rekey via anchor-preserving delegation chains](019-gitback-founder-rekey.md) — `project_id` stays anchored to the genesis founder pubkey forever; per-project `DelegationEnvelope` chain bridges retired founder pubkeys to the current signing identity; authority windows close the deposed-founder + antedated-token attacks; `re-invite-all` + `rejoin` mediate cross-puddle member rejoin via fresh OOB capability codes; `re-found` is the escape hatch when the chain hits cap. - [ADR-020: Lockbox is puddle-only](020-lockbox-puddle-only.md) — standalone mode retired in 0.40.0; supersedes ADR-016's standalone branch (recipient-resolution and per-envoy-key decisions stand). Mode 1 (encryption-at-rest, no peers) handled via single-envoy puddle. `WrapMode` enum + dual-mode unlock paths + pairwise-gossip recipient resolution all retire. No migration verb — operators with existing standalone enrollments scrub-and-re-enroll under puddle.
- [ADR-021: Lockbox lifecycle absorbed into puddle](021-lockbox-lifecycle-on-puddle.md) — sibling to ADR-020 in 0.40.0. Lockbox's per-capability lifecycle (`init`, `leave`, `forget <host>`) folds into puddle (`puddle init`/`join` auto-enroll, new `puddle leave`, new `puddle evict <host>`); lockbox subtree shrinks to content-only verbs. - [ADR-022: Friendly gitback names (puddle/repo)](022-gitback-friendly-names.md) — `gitback://<puddle-name>/<repo-handle>` layered on the self-certifying hex pid; puddle names are first-come, gossiped-via-traits, ambiguous-on-collision (no auto-tiebreak); the server publishes the fleet name map without arbitrating; `re-found` auto-re-issues the claim (the `supersedes` field carries the rekey-delegation chain). Friendly names are a convenience, the hex pid is the proof — spoofable by squatting, stated loudly. Forking = `clone` + `project init` (GitHub-fork semantics; fork ≠ mirror, history forever). Implemented in 0.42.0; `public_read` is a separate ADR. (0.48.0: `RESOLVE-NAME` falls back to the requesting user's own `name-claim.json` on a fleet-map miss, so a fresh claim resolves from the claiming envoy immediately.)
- [ADR-023: Puddle-wide gitback project adoption](023-gitback-puddle-wide-adoption.md) — **implemented in 0.49.0.** A puddle member envoy auto-adopts the projects its puddle founded at `puddle unlock` time, so `dr_scope: swarm-wide` repos actually reach the puddle's other envoys (before this, `project init` wrote per-user state only on the founding envoy → `HOSTS 1` forever). Widens the `GITBACKPROJECT:` announce to carry `<handle>:<dr_scope>` (the legacy 2-field form still parses during a rolling agent upgrade); the catch-up reactor flushes a world-readable `gitback-announced.json` each tick; `puddle unlock` (the one spot that runs as the user with a freshly-spawned session helper) mints founder-bootstrap state for any announced project where `sha256(local_puddle_pubkey ‖ handle) == pid` and there's no local state, then the existing DR-catch-up reactor pulls the bytes. Founder-current-key only (post-rekey projects use `rejoin`); no new attack surface (self-minting a bootstrap is what `project init` already does).

- [ADR-024: curator — P2P artifact registry](024-curator.md) — **implemented in 0.51.0.** A fifth swarm content subsystem: filecast's content-addressed blob transport + gitback's puddle-keyed identity/access machinery + a thin catalog layer. Artifacts (release binaries, tarballs, `.deb`/`.rpm`, container images, the agent's own self-update binaries) keyed `sha256(founder_puddle_pubkey ‖ name)`, referenced `<puddle-name>/<name>:<tag>` (operator puddle = the implicit default namespace); a single founder-signed catalog entry per artifact (mutable tags, multi-arch `platforms:[{os,arch,blob_sha,size}]`, `recipients:["*"]`-by-default, a `target` scope), re-signed LWW on every change, gossiped P2P + aggregated server-side. **Write side is puddle-members-only** (`vigo swarm curator push/tag/rm/prune/…`, gated by `swarm.curator.enabled` × usercrate `curator: bool` × an unlocked puddle; `vigocli` is the operator front-end onto the same `/var/run/vigo/curator.sock`). **Read side is server-mediated and universal** — every envoy, swarm-enabled or not, resolves `<name>:<tag>` via the server (which enforces `recipients`) then pulls the bytes P2P or relayed from the server, and materializes to `/var/lib/vigo/artifacts/…` + `cache.json`. Documented limits: "restrict access" = per-envoy materialization-gating, not byte-confidentiality (raw DR bytes are root-readable on every `target`-matched envoy — lockbox owns confidentiality); the server owns resolution (outage stops new pulls fleet-wide). Consumers (`artifact:` executor param, Docker Registry v2 shim, agent-self-update accelerator) are post-v1 slices. A signed, immutable `kind` discriminator (`generic`/`oci-archive`/`apt-repo`/`dnf-repo`/`apk-repo`) on each catalog entry tells the consume facades apart and lets a facade refuse a wrong-shape artifact cleanly — slice 9, 0.66.24 (see the ADR Addendum). A package-repo facade — slice 10, 0.66.26 — serves a private apt/dnf/apk repository at `http://127.0.0.1:<local_port>/repo/<name>/…` out of an `apt-repo`/`dnf-repo`/`apk-repo` artifact (a plain `.tar` of a signed repo tree), consumed by a stock `repository` resource with no repo server. Supersedes the "Artifact — P2P container image distribution" post-v1 entry (generalized); the deferred public-read-gitback feature is its git-content sibling.
- [ADR-025: stacks-in-gitback — service-account puddle + ops-puddle ownership](025-stacks-in-gitback.md) — **approved 2026-05-16, not yet implemented.** Pre-Phase-0 design for the spanner redesign. Vigosrv runtime user gets a service-account puddle identity at `/srv/vigo/puddle/identity.wrapped`, wrapped under a key derived from the existing secrets master key via `HKDF-SHA256(master_key, "vigo-puddle-wrap-v1", per-host-salt)`. Extends ADR-014's per-human puddle primitive to service accounts. A dedicated **ops-puddle** (operator-named, e.g., `alexander4-ops`) collectively owns the stacks gitback project; founder = first vigosrv; subsequent vigosrvs join via the standard ADR-014 puddle-pair flow. Stacks distribution becomes a single gitback project (`gitback://<ops-puddle-name>/stacks`) with `dr_scope: swarm-wide`; every vigosrv pulls and triggers config reload via a gitback-event-driven watcher reusing the existing helper-daemon notification pubsub. `vigocli config publish` switches behavior on deployment shape: standalone writes local-filesystem-and-SIGHUPs (today); spanner commits + pushes to the gitback project and waits for the local watcher to confirm. No backwards-compat bridge with `Hub.SyncConfigToSpokes` — Phase 0 retires that path entirely. Five slices; gates the spanner redesign's Phase 0.
- [ADR-026: Peer-equal admissions over multicast-gossiped LWW-Map](026-spanner-peer-equal-admissions.md) — **approved 2026-05-19, not yet implemented.** Slice 2A of the spanner redesign Phase 2. Replaces Phase 1's in-memory `Hub.boltPins` map with a peer-replicated LWW-Map CRDT on `spanner_bolts` (keyed by pubkey, revoke-wins). Admissions atomically coupled to the `consumed_tokens` G-Set via FK constraint — admission row insert + token-hash insert land in one transaction; the two CRDTs cannot be sliced apart. Transport is two-tier: Tier-1 counters gossip on new multicast group `224.0.0.45:1534` every 30s, Tier-2 roster bytes serve over `GET /api/v1/spanner/snapshots/<pubkey>/<seq>` on existing 8443 REST. New `JoinSpanner` admin gRPC for the admission ceremony — joining bolt presents one-time invite token to any reachable peer; peer atomically inserts admission + consumes token + signs the new row. Hub stays as a bootstrap-discovery rendezvous in 2A only — it's now a peer (`mode: founder`) with the same membership shape as everyone else; full retirement at Phase 3. `server.yaml` migration is hard-error: retired fields (`hub_addr`, `hub_fallback_addrs`, `spokes`, `auto_failover`, `role`) refused at load with a one-line pointer to their replacements (`mode`, `spanner_id`, `patterns`, `snapshot`, `transport`, `freshness`, `fallback_admin`). Bakes in five operator-question decisions ratified during 2026-05-19 scrutiny: pattern-conflict refuse-layered, 24h join-token TTL with `--ttl` override, invite stdout-default + TTY warning, `init` requires `spanner_id` pre-set in `server.yaml`, hostname re-announce is restart-only (no rename verb in v1). Out of 2A scope: vigocli `invite`/`approve`/`revoke`/`leave` verbs (2B), license-attestation observability (2C), full multi-vigosrv test harness (2D). Supersedes the withdrawn 2026-05-18 draft (commit `31aba7a1` added; commit `05f95938` withdrew) that diverged from the plan on 8 substantive axes.
- [ADR-027: curator S3 object-storage API](027-curator-s3-api.md) — **approved 2026-05-22, implementation in progress.** A read-only, S3-compatible HTTP API on vigosrv exposing curator artifacts as S3 objects, so non-envoy clients (CI runners, dev laptops, any S3 SDK) can fetch curator content — `aws s3 cp` works unmodified. Composition, not new protocol: `curatormesh.Snapshot()` is the catalog SoT, `ResolveVersion`/`ResolvePlatform` already do key→blob resolution, and the existing blob relay's `http.ServeContent` gives ranged GET of 2 GiB blobs for free; the only new code is SigV4 verification. Surface: `GetObject`/`HeadObject`/`ListObjectsV2`/`ListBuckets` (writes → S3 XML `405`); one fixed bucket `vigo-curator`, key `<publisher>/<artifact>/<version>/<os>-<arch>`. A dedicated, opt-in HTTPS listener (`swarm.curator.s3_port`, `0` = disabled) reusing the server TLS material — not co-hosted on `:8443` (own SigV4 middleware + XML errors). Two auth paths, deliberately not unified: mTLS stays for envoy curator reads, SigV4 authenticates only the S3 surface. SigV4 credentials are **derive-don't-store** — the `secret_access_key` is `LocalProvider.DeriveKey("vigo-curator-s3-cred-v1", access_key_id, 32)`, recomputed at verify, never persisted; the credential row is pure metadata; minted via `vigocli swarm curator s3-credentials`. Requires the `local` secrets backend in v1 (the derivation roots in the master key — master-key rotation invalidates every credential at once). Five slices; new `server/curators3/` package.
- [ADR-028: Trace-ID propagation for cross-process log correlation](028-trace-id-propagation.md) — **approved 2026-05-23, implementation in progress.** W3C `traceparent` carried in the proto message body of every agent-initiated request and relevant server-pushed event; both sides extract the 32-hex trace_id portion and surface it as a slog (server) / `tracing` (agent) field, and the integrations event dispatcher includes it in `Event.Details["trace_id"]`. Proto-body rather than gRPC metadata because the persistent `AgentStream` multiplexes many logical operations under one metadata frame — per-call metadata can't give per-operation granularity for streamed RPCs. Always-on; no `tracing:` config, no toggle. `trace_id` is exclusive to slog / `tracing` / integrations payload — explicitly **never** a Prometheus metric label (cardinality firewall). Coverage: agent→server (`CheckInRequest`, `ReportResultRequest`, `ReportTraitsRequest`) plus server→agent push (`TaskDispatch`, `ForcePush`, `PolicyPush`); `TunnelStream` and audit-record trace_id deferred. Forward-compatible with a deferred full-OTel follow-on — adopting `otelgrpc` later consumes the same `traceparent` value and adds spans without changing the wire shape.
- [ADR-029: poolq — P2P ordered-log queue](029-poolq.md) — **approved 2026-05-23, implementation in progress.** A sixth swarm content subsystem: a Kafka-style ordered log replicated fleet-wide via the trait → mesh → check-in propagation pattern. Topics keyed `sha256(founder_puddle_pubkey ‖ topic_name)` (the gitback `project_id_for` / curator `artifact_id` shape); referenced `poolq://<puddle-name>/<topic_name>` (hex form always works). Each message is a signed envelope `{topic_id, seq u64 (founder monotonic), msg_id, body (16 KiB default, 64 KiB ceiling), posted_at, author_pubkey, signature}` with `seq` covered by the signature; new anchor signing domain `poolq-msg-v1\0`. Per-topic G-Set CRDT keyed by `msg_id`, merge = union, log = sorted by `seq`; age-based retention (7d default) + stale-on-ingest refusal → flap-stable pruning with no tombstones. Founder-only posting in v1; multi-writer delegation (ADR-019 chain) deferred to v2 alongside the RabbitMQ-style competing-consumer work queue (`deferred.md`). Two-layer authorization mirrors curator (`swarm.poolq.enabled` × usercrate `poolq:` × unlocked puddle). Consumer offsets are local-only, never replicated; `~/.vigo-poolq/subscriptions.json` per user. Replication rides the existing check-in cadence (minutes-fresh) — the multicast Tier-1 fast-path is a post-v1 lever. **Confidentiality is not a goal** — pair with curator for large payloads, lockbox for confidential payloads. Five slices.
- [ADR-030: Spanner webusers CRDT — cross-bolt user replication + session invalidation](030-spanner-webusers-crdt.md) — **approved 2026-05-24, not yet implemented.** Extends ADR-026 to the `users` table: LWW-Map keyed on `users.id`, comparator on `updated_at_ms INTEGER` (unix-ms) with `origin_bolt` pubkey-hex tiebreaker, soft-delete via `deleted_at` column (mirrors `spanner_bolts.revoked_at`), per-row signing by writing bolt (verified end-to-end on merge). Rides ADR-026's existing Tier-1 multicast / Tier-2 REST snapshot pull — `Snapshot{Roster, ConsumedTokens, Users}`. Session invalidation is on-merge (not a separate broadcast): the merge handler runs `auth.SessionManager.DestroyUserSessions(userID)` when role changes or `deleted_at` flips. Convergence latency for the destroy signal equals CRDT convergence latency — ≤30s via Tier-1 fast-path, ≤5min worst-case. Six slices (2-iii-a ADR through 2-iii-f upgrade ergonomics). Deliberate trade-offs: sub-30s session invalidation instead of sub-second (no peer-RPC); pre-existing multi-bolt webusers conflict on first replication (lex-min-pubkey wins, documented); `totp_recovery` replication needs a peer-portable encryption shape (resolved in Slice 2-iii-c). Direction-call from Dan 2026-05-24 picked option (a) from the pending entry — replicate via CRDT, not document the per-bolt-update constraint.
- [ADR-031: Agent baked-in signing key for self-update verification](031-agent-baked-in-signing-key.md) — **approved 2026-05-24, implemented in 0.66.93.** Fixes the CLAUDE.md "self-updates only from ed25519-signed binaries" guarantee, which the prior implementation violated along two paths (server omitting signature → `debug!` skip; signing-key fetch failure → `warn!` skip). Deeper bug: even with fail-close, fetching the verification pubkey from the same server that delivered the binary is circular — a fully-compromised server returns attacker-chosen pubkey + signature and verification "succeeds." Replaces server-fetched pubkey with a build-time-baked-in pubkey injected via `env!("VIGO_AGENT_SIGNING_PUBKEY")` from the same `SIGN_KEY` that signs `.sig` files (one private key, two consumers, no drift possible). `verify_signature_or_bail` is the single entry: bails on empty signature, on the dev sentinel pubkey (32 zero bytes baked in when plain `cargo build` runs without `SIGN_KEY`), or on verification mismatch. `fetch_signing_key` deleted from the agent; server endpoint preserved for bootstrap scripts + operator debugging. Dev-mode sentinel chosen over cargo feature flag (avoids coupling runtime behavior to a compile-time toggle the build system has to remember) or hard build failure (would break every cargo workflow for anyone without signing set up). Rotation deferred to post-v1 — single key today means key rotation = fleet-wide redeploy; multi-key transition-pair pattern is the post-v1 lever and is tracked in pending.
- [ADR-032: Envoy tree navigation — directory-hierarchy view alongside the flat envoys table](032-envoy-tree-navigation.md) — **approved 2026-05-24, slice 1 implemented in 0.67.2.** The flat `/envoys` table works for low-thousand fleets but doesn't scale past that; operators need to *navigate* the fleet, not scroll through it. New `/envoys/tree` page walks the same `.live/` filesystem the `/fleet/config-tree` page renders, and at each directory node lists the envoys whose matched hostcrate sits in that directory — pure join of `FleetIndex.AllEnvoys()` × `ConfigStore.Match()` × `ConfigStore.MatchDirPaths()`, no new SoT. Coexist (not replace) with the flat view — flat is genuinely better for small fleets; tree solves a different navigation problem. Click-through to existing `/envoys/{id}` detail (no in-page pane); chip pattern carries over from flat for filter consistency; `<details>` collapse-expand (no JS); tree-expansion state in `localStorage` (URL parameters stay reserved for filter state). Synthetic `(unmatched)` node surfaces envoys with no matched hostcrate as a triage bucket. Slice 2 (tag/role/OS chips on both views + faceted hide-empty-branches behavior) tracked in pending; slice 3 (HTMX lazy-load per branch) deferred until a real fleet exercises the cost.
- [ADR-033: Conditional traits transmission — vitals/inventory split](033-traits-delta-encoding.md) — **accepted 2026-06-04, implemented (first cut) in 0.74.11 (proto `82a24b5e` / server `4df7ca36` / agent `c850416b`); dormant until the fleet is rebuilt/redeployed.** The agent re-sends the full `traits_json` (~220-330 KB measured on the real fleet) every check-in, and the fleet is network-bound — so the wire cost is the bottleneck. A whole-payload hash gate is dead (live `uptime`/`time`/`loadavg`/`memory`/`swap` change every collection). The spike found the per-cycle churn is only **~5 KB / 2%** and that the agent **already** classifies collectors into volatile / stable / periodic (`CachedCollectors`, `volatile_collectors()`) — so the right design is to split the wire into **vitals** (the volatile set, sent every check-in) + **inventory** (stable+periodic, ~213 KB, sent only when its hash changes, with a `resend_inventory` self-heal on desync), reusing the existing classification with no diff/patch machinery. The swarm collectors are volatile → sent every cycle → swarm-ingest heartbeat is untouched (no freshness-decouple needed); the server caches inventory onto the FleetIndex flattened form (no ~13 GB structured baseline). ~98% steady-state wire cut. Delta encoding (JSON Merge Patch) was the original decision, kept as the fallback if a stable collector proves non-deterministic. Rejected gRPC compression as the answer (~5× but trades the network bound for ~1 ms/check-in server decompress CPU; kept as an orthogonal follow-on). Residual: stable collectors must serialize deterministically (audit `security_scan`/`cert_lifecycle` for scan timestamps). Cross-cutting proto/agent/server, Linux-first.
- [ADR-034: AgentStream per-message ed25519 verification](034-agentstream-per-message-signature-verification.md) — **accepted, implemented in 0.74.15.** The unary RPCs enforce the per-request ed25519 signature invariant via the unary `SignatureVerifyInterceptor`, but the persistent `AgentStream` (bidi) bypassed it: recovery-only stream interceptor, handshake checked only `envoy_id` existence/revoked, read loop dispatched multiplexed `CheckIn`/`ReportResult`/`ReportTraits` straight to handlers with no signature check. mTLS alone authenticated the channel — and mTLS doesn't bind identity here (`RequireAndVerifyClientCert` against the shared CA, cert CN = hostname, never cross-checked against the claimed `envoy_id`), so any enrolled envoy could open a stream as any other `envoy_id` → insider cross-envoy impersonation, a silent violation of the stated invariant. An oversight, not a trade-off: the sibling `TunnelStream` already verifies its handshake. Fix verifies the handshake (binds the stream to the enrolled key; TLS integrity covers the rest) + every signed multiplexed message via the existing helpers (`fleetIndex.Verify` fast path); proxied `ReportResult` now verifies the device's signature. Server-only (agents already sign every stream message). Rejected cert-CN→`envoy_id` binding as weaker (no per-request non-repudiation, hostname-coupled) when the signatures are already on the wire.
- [ADR-035: Application-layer gzip for large policy-bundle responses](035-policy-bundle-response-compression.md) — **accepted, implemented in 0.74.19.** ADR-033's named follow-on for the server→agent side: compress the policy bundle on the wire. The obvious mechanism (register gzip codec + `grpc.SetSendCompressor`) is a trap — bundles ride `AgentStream` as a `CheckInResponse` inside `ServerStreamMessage`, the same wire message as every tiny ack (`no_change`, `report_result_ack`, `delta_ack`), and `SetSendCompressor` is set-once-per-stream with no per-message/size threshold, so it would gzip every heartbeat fleet-wide (framing > savings on tiny payloads + per-message CPU) — a steady-state regression on the convergence-critical path. Instead, compress at the **application layer**: new `CheckInResponse.policy_bundle_gzip` (`bytes`, field 26) carries `gzip(proto.Marshal(bundle))` when the marshaled bundle exceeds 4 KiB and actually shrinks, leaving the structured `policy_bundle` nil; the agent inflates it back at every reception point so downstream stays bundle-shaped. **Zero steady-state cost** — bundles ship only on config-change (the `no_change` path returns earlier), never on the heartbeat/ack path. **Signature-transparent** — the bundle sig is over content fields (`marshalBundleContent`), not wire bytes, so the gzip round-trip preserves it; ADR-034's per-message verify is agent→server only. `compressBundle` lives in the single `buildCheckInResponse` chokepoint (covers unary + both stream sites); `flate2` direct on the agent (already in the graph via `age`), Go stdlib `compress/gzip` server-side; no tonic `gzip` feature. `StreamPolicyPush` left untouched (dead — config-change pushes go via `ForcePush` + re-check-in).
